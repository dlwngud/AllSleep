# AllSleep 제품 개편 단계별 구현 로드맵

작성일 2026년 10월 12일

이 문서는 PRODUCT-PLAN.md와 SCREEN-SPEC.md의 67개 화면을 실제 앱으로 구현하기 위한 작업 순서다. 한 단계씩 독립적으로 요청하고 검토할 수 있도록 선행 조건, 구현 범위, 완료 기준과 검증을 정의한다. 이번에 수행한 일은 계획 작성이며 아래 구현 단계는 아직 실행하지 않았다.

## 1. 진행 방식

단계 번호는 이후 요청과 진행 기록의 기준으로 고정한다. 예를 들어 “이 로드맵의 07단계를 구현하고 검증까지 진행해줘”라고 요청하면 된다. 각 단계는 필요한 조사, 구현, 의미 있는 검증, 문서 갱신, 다음 단계에 넘길 결과까지 포함한다. 화면을 그리거나 성공처럼 보이는 임시 데이터만 연결한 상태를 완료로 인정하지 않는다.

작업 시작 시 현재 코드와 진행표를 다시 확인한다. 앞 단계가 실제로 완료되어 있지 않다면 그 선행 조건을 구체적으로 식별한다. 수정 범위 안에서 해결할 수 있는 문제는 처리하고, 새 단계에 해당하는 큰 변경은 범위를 분명하게 설명한다. 예상 시간이 길다는 이유로 중요한 예외 처리를 생략하지 않는다.

매 단계 종료 보고에는 변경한 사용자 동작, 실제 구현된 상태, 실행한 검증과 결과, 남은 외부 조건, 데이터 이관·되돌리기 영향, 다음 단계 준비 여부를 포함한다. 기기나 스토어 계정이 없어 실행하지 못한 검증은 “통과”로 표시하지 않는다.

진행 상태는 IMPLEMENTATION-STATUS.md에 기록한다. 문서·시안의 준비 완료와 앱 구현의 완료를 구분한다. iOS 단계는 별도 선택이며 Android 출시의 선행 조건이 아니다.

## 3. 현재 코드에서 먼저 고려할 사항

2026년 10월 12일 읽은 코드 기준의 관찰이다. 각 구현 시점에 다시 확인한다.

- 현재 App.kt는 비로그인 사용자를 홈에서 로그인으로 이동시킨다. 화면에서 로그인 버튼을 숨기는 것만으로 게스트 기능이 완성되지 않는다.
- 현재 SleepRecordRepository의 조회는 uid에 의존하고 Android 구현은 Firestore를 사용한다. 독립적인 로컬 원본 저장이 필요하다.
- 현재 기록 저장은 날짜를 문서 ID로 사용한다. 같은 밤 여러 번 시작·종료하면 기존 회차를 덮을 수 있으므로 새 구조는 회차와 세션 ID를 사용해야 한다.
- 현재 AppBlockerRepository는 시스템 앱 여부만 판별한다. 사용자 선택 앱·항상 허용 앱 정책을 표현하는 계약이 필요하다.
- 서비스 내부에도 계정 상태와 원격 상태 의존이 있다. 로컬 제한과 해제는 인증·인터넷 연결과 분리해야 한다.
- verify.sh는 Android 디버그 컴파일·린트·단위 테스트를 수행한다. 실기기 자동 시작·해제·접근성·실제 스토어 구매 검증을 대신하지 않는다.
- 빌드 설정에는 광고 설정의 필수값 검사가 있다. 광고 제거 시 SDK·코드와 함께 빌드 설정과 매니페스트 의존도 정리해야 한다.
- 서버 보안 규칙·배포된 함수·RevenueCat 설정은 현재 읽은 저장소만으로 모두 확인되지 않았다. 실제 운영 구성을 파악하고 재현 가능한 소스와 테스트를 갖춰야 한다.
- 현재 미커밋 변경과 기존 작업 공간이 있다. 이 계획에 포함되지 않는 변경을 임의로 정리하거나 되돌리지 않는다.

## 4. 단계별 작업

### 01 현재 상태와 구현 기준 확정

**선행 조건:** 기획서와 화면 시안 준비.

**작업:**

1. 현재 브랜치, 미커밋 변경, 연결된 작업 공간, 기존 릴리스 상태를 확인한다. 작업에 필요한 변경의 포함·보존 방식을 기록한다.
2. 현재 앱을 빌드하고 verify.sh의 실제 실행 결과를 확보한다. 기존 실패와 개편으로 생긴 실패를 구분한다.
3. 실제 화면과 시안의 차이, 계정·서비스·기록 의존, 현재 구독자의 이전 정책을 목록으로 만든다.
4. 취침 30분 전 약속 스냅샷, 10분 정시 기준, 임시 사용 5분, 기기 5대, 체험과 가격 등 기획 가설을 구현 가능한 설정값으로 분류한다.
5. 새 지침과 구현 기준에 영향을 주는 문서 충돌을 정리한다. 사용 흐름 시안의 열람 순서를 실제 분기 그래프로 구체화한다.

**완료 기준:** 기준 버전과 보존 대상, 실제 검증 결과, 구현 결정 목록, 외부 서비스·기기 검증 준비 사항이 문서화되어 있다. 시안 속 “실행 확인 결과 보기”는 실제 앱의 자동 상태 갱신으로 구현한다는 기준도 명시한다.

**검증:** 기존 앱 동작 확인과 기준 빌드·테스트 결과 확보. 아직 앱 기능을 개편한 것으로 표시하지 않는다.

**산출물:** 기준 상태 기록, 구현 결정 기록, 검증 목록. 이후 단계는 이 기록을 기준으로 진행한다.

### 02 빌드와 검증 기반 정리 및 광고 제거

**선행 조건:** 01.

**작업:**

1. AppOpenAd 경로, 광고 SDK, 의존 주입, 매니페스트 값, 광고용 빌드 설정과 필수값 검사를 함께 제거한다.
2. 디버그와 출시 빌드의 차이, 결제 테스트 설정, 실제 서명 설정의 취급을 분리한다. 비밀값을 문서나 로그에 기록하지 않는다.
3. 기존 단위 테스트에 도메인·로컬 저장·서비스 경계의 실패를 검증할 테스트 기반을 마련한다.
4. UI의 중요한 상태와 접근성을 검수할 환경을 마련한다. 테스트 도구는 현재 프로젝트와 호환되는 범위에서 선택한다.
5. verify.sh의 실제 검증 범위를 명확하게 하고 출시 빌드·실기기 검수와 구분한다.

**관련 화면:** 전체 화면의 광고 없는 공통 경험.

**완료 기준:** 광고 설정 없이 디버그 앱을 실행할 수 있다. 핵심 경로에 광고가 남지 않는다. 테스트를 실행하는 방법이 실제 저장소와 일치한다.

**검증:** 디버그 컴파일·린트·단위 테스트, 가능한 출시 빌드 확인. 외부 서명이나 스토어 준비가 없으면 별도 상태로 기록한다.

### 03 디자인 시스템과 공통 화면 구조

**선행 조건:** 02.

**작업:**

1. 네이비·보라색·라벤더·상태색·타이포그래피·여백·모서리를 공통 토큰으로 정의한다. 기존 캐릭터 자산을 재사용한다.
2. 주 행동 버튼, 설정 행, 카드, 선택 항목, 상태 안내, 입력 오류를 공통 컴포넌트로 만든다.
3. 오늘·루틴·기록·마이 탭과 상세 화면 구조를 구성한다. 제한 중 화면에서는 탭과 일반 닫기를 숨긴다.
4. 로딩·빈 상태·오류·부분 데이터·오프라인을 표현하는 공통 규칙을 정의한다.
5. 시스템 상하단 영역과 키보드, 360dp 폭, 큰 글꼴과 스크린리더를 고려한다. 가로·큰 화면에서는 불필요하게 늘어나는 입력·버튼 너비를 제한한다.

**관련 화면:** 전체 공통 구성.

**완료 기준:** 이후 화면들이 같은 공통 컴포넌트와 토큰을 사용한다. 실제 화면은 프리뷰와 실행 화면에서 같은 구조를 유지한다.

**검증:** 대표 화면 상태의 시각 확인, 터치 영역·읽기 순서·키보드·시스템 영역 확인. 실제 제품 동작은 이후 단계에서 연결한다.

### 04 취침 회차와 실행 상태 모델

**선행 조건:** 01. UI 구현과 독립적으로 진행할 수 있으나 단계 번호는 유지한다.

**작업:**

1. 루틴, 오늘만 예외, 약속 스냅샷, 제한 세션, 기기별 실행, 임시 접근, 자기 보고, 구독 자격의 공통 계약을 정의한다.
2. 취침 날짜 기준 회차 ID와 고유 세션 ID를 사용한다. 자정 이후 해제 날짜를 명확하게 계산한다.
3. 준비 필요·예약·시작 요청·실행 확인·제한 중·종료 요청·해제 확인·미확인·중단을 분리한다.
4. 상태 전환과 명령 버전을 정의해 늦은 시작 응답이 최신 종료를 덮지 않게 한다.
5. 날짜 경계·시간대 변경·일광절약 시간·같은 시작과 해제·일정 충돌·사후 계획 변경의 규칙을 정한다.
6. OS 실행 확인을 전달할 플랫폼 계약과 구독 여부에 따라 기능을 제공하는 계약을 만든다. 기존 라이브러리를 일괄 교체하지 않고 필요한 경계를 정리한다.

**관련 화면:** H06, N01, N05, X01, X02와 모든 시간·기록 화면의 기반.

**완료 기준:** 서버 상태 저장만으로 실행 완료가 될 수 없는 모델이다. 시간과 상태 계산은 플랫폼 UI에 의존하지 않는다.

**검증:** 자정 경계, 시간대 변경, 중복 요청, 지연 응답, 최신 종료 유지, 약속 스냅샷 변경의 도메인 테스트.

### 05 로컬 저장과 기존 기록 이관

**선행 조건:** 04.

**작업:**

1. 루틴·회차·기록·선택 앱·임시 접근을 계정 없이 저장하고 다시 읽을 수 있는 저장소를 구현한다.
2. 로컬 소유자를 명시해 게스트와 로그인한 계정의 데이터를 구분한다. 로컬 원본과 클라우드 복제 상태를 분리한다.
3. 날짜 하나가 아니라 세션 ID 단위로 기록을 저장한다. 같은 밤 여러 번 시작해도 덮어쓰지 않는다.
4. 현재 설정과 기존 SleepRecord의 이관·호환 읽기를 설계한다. 확인 구간이 없는 기존 기록은 “기존 방식 기록”으로 보존한다.
5. 기존 기록에 없는 임시 사용·관찰 공백·기기 실행 확인을 만들어 넣지 않는다. 새 정시·유지 지표는 계산 가능한 회차만 사용한다.
6. 쓰기 실패, 앱 강제 종료, 부분 이관 후 재시작에도 원본이 남고 다시 시도할 수 있게 한다.

**완료 기준:** 앱 종료·재실행과 인터넷 단절 뒤에도 설정과 기록이 남는다. 이관은 중복 실행에 안전하고 기존 원본을 보존한다.

**검증:** 저장 실패, 중복 세션, 중단된 이관, 데이터 재읽기, 다른 로컬 소유자 접근 격리. 저장 기술은 실제 회차 데이터와 이관 요구를 기준으로 선택하고 근거를 기록한다.

**검증:** 실제 실기기·여러 기기·플랫폼 결제 테스트와 자동 회귀 검증. 스크린샷이 같다는 이유만으로 기능 완료를 인정하지 않는다.

### 26 Android 출시 준비와 파일럿

**선행 조건:** 25.

**작업:**

1. 가격·상품·체험·지원 플랫폼·지원 기기 수 등 검증 후 확정한 판매 조건을 반영한다.
2. 접근성 고지와 선언·필요 권한·스토어 콘텐츠·데이터 처리 안내를 실제 구현으로 준비한다.
3. 내부 테스트나 파일럿 후보를 패키징하고 재현 가능한 배포·되돌리기 절차를 작성한다.
4. 파일럿에서 첫 설정·실행 성공·정시 변화·실패 원인·유료 가치와 가격 가설을 확인한다.
5. 리뷰 결과에 따라 작은 조정을 반영하고 유효한 결과와 기술 오류를 분리해 기록한다.
6. 실제 배포를 요청받은 범위에 맞춰 진행한다. 출시 준비 완료와 스토어 심사 승인·공개 배포 완료는 구분한다.

**완료 기준:** 검증된 출시 후보와 배포 문서, 확정 판매 범위, 파일럿 결과 또는 파일럿 실행에 필요한 외부 조건이 명확하다.

**검증:** 배포 후보 설치·업데이트·서명·실제 상품·스토어 진입·이관·긴급 접근. 심사 대기와 실제 사용자 모집은 코드 구현 완료와 다른 상태로 기록한다.

### 27 iOS 지원 가능성 확인 선택

**완료 기준:** 지원 범위와 승인 상태, 실기기 검증 근거가 있다. 기술 가능성·승인 대기·출시 가능을 구분한다.

## 6. 요청 문장

기본 요청은 다음 문장을 사용한다.

> IMPLEMENTATION-ROADMAP.md의 NN단계를 구현과 검증까지 진행해줘. 해당 단계의 범위를 승인하고, 기존 사용자 변경과 데이터를 보존해줘. 완료 기준을 실제로 확인한 뒤 IMPLEMENTATION-STATUS.md에 결과와 다음 단계 준비 상태를 기록해줘. 실행하지 못한 검증은 미검증으로 표시해줘.

읽기 전용 단계인 01은 “현재 상태 확인과 기준 문서화를 진행해줘”라고 요청할 수 있다. 해당 요청은 이후 모든 구현 단계나 공개 배포를 한꺼번에 승인하는 뜻이 아니다. 큰 단계는 문서에 적힌 하위 작업 번호로 나누어 요청할 수 있으며, 하위 작업만 끝났을 때 상위 단계 전체를 완료로 바꾸지 않는다.
