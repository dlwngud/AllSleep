# AllSleep agent.md 개편 제안

작성일 2026년 10월 12일 · 29단계에서 실제 구조를 반영해 확정할 초안

이 문서는 지침 개편의 구성안이다. 이번 작업에서 프로젝트 루트의 agent.md나 AGENTS.md를 변경하지 않았다. 아래 초안은 현재 적용 중인 지침을 대체하지 않는다.

## 1. 지침이 담당할 일

지침은 어떤 제품을 만드는지, 어떤 원칙을 유지해야 하는지, 어디에서 자료를 읽고 작업하는지, 무엇을 실제 완료로 인정하는지를 짧게 전달해야 한다. 진행 일지와 모든 기술 설명을 지침에 넣으면 현재 작업에 필요한 기준이 잘 드러나지 않고 오래된 내용이 남기 쉽다.

루트 지침은 제품 원칙과 작업 규칙을 중심으로 두고, 상세 기획·화면 명세·구현 순서·진행표를 링크로 연결한다. 실제로 변경된 구조와 명령은 해당 문서에서 관리한다. 29단계에서 이 링크와 명령이 실제 저장소와 일치하는지 확인한다.

## 2. 파일 이름과 배치

Codex용 프로젝트 지침은 루트 **AGENTS.md**를 단일 기준으로 쓰는 구성을 권장한다. OpenAI 공식 문서는 AGENTS.md와 경로별 override 및 별도 fallback 이름의 발견 규칙을 설명한다. 현재 이름인 agent.md의 자동 인식 설정은 확인하지 않았으므로, 그 이름만으로 자동 적용된다고 가정하지 않는다. [OpenAI 공식 지침 파일 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

다른 도구나 사용 습관 때문에 agent.md가 필요하면 파일에는 단일 기준 AGENTS.md를 읽으라는 안내와 링크만 남기는 구성을 권장한다. 두 문서에 같은 작업 규칙을 복사해 서로 다른 버전으로 만들지 않는다. 다른 도구가 링크를 자동으로 읽는지는 해당 도구에서 확인한다.

초기에는 루트 지침 하나로 시작한다. Android·iOS·서버의 고유 규칙이 실제로 필요할 때만 해당 작업 경로의 지침으로 나눈다. 민감한 권한·실행·결제의 원칙은 루트에도 짧게 유지한다.

아래는 작성 기준이 되는 완성 형태의 초안이다. 29단계에서 실제로 완성된 플랫폼·폴더·검증 명령·문서 위치에 맞춰 갱신한 뒤 적용한다.

## 제품 목적

AllSleep은 자야 한다는 것을 알면서도 디지털 기기를 계속 사용해,
스스로 정한 취침 시간을 지키지 못하는 문제를 해결한다.
기능과 화면을 변경할 때 취침 전 기기 사용을 마무리하는 데 어떻게 기여하는지 확인한다.

## 유지할 제품 원칙

- 한 기기의 기본 취침 약속, 제한, 예정 해제, 긴급 접근, 원본 기록은 무료다.
- 로그인과 결제 없이 첫 사용을 완료할 수 있어야 한다.
- Plus는 지원 기기 연동, 복수 루틴, 기록 비교와 조정의 반복 가치를 제공한다.
- 잠금 유지 시간을 실제 수면 시간으로 표현하지 않는다.
- 요청·예약·실행 확인·해제 확인·미확인·기술 중단을 구분한다.
- 전화와 긴급 기능, 이 기기의 즉시 해제는 광고·결제·원격 응답으로 지연하지 않는다.
- 서비스·계정·구독·네트워크 오류가 무료 로컬 기능과 해제 경로를 막지 않게 한다.

- 보라색·네이비·캐릭터를 포함한 디자인 토큰과 공통 구성 규칙을 사용한다.

## 기준 자료

작업 범위에 필요한 문서만 읽는다.

제품과 시안의 중요한 차이가 생기면 근거를 기록하고 관련 문서를 함께 갱신한다.
시안의 예시 가격·기록·완료 버튼을 실제 서비스 데이터나 성공 응답으로 사용하지 않는다.

## 코드 구조

- 공통 UI·상태·도메인: composeApp/src/commonMain/kotlin/com/wngud/allsleep
- Android 구현: composeApp/src/androidMain/kotlin/com/wngud/allsleep

OS 권한·서비스·예약·인증·결제는 플랫폼 구현으로 처리한다.
기존 라이브러리와 구조를 존중하고 목적과 관계없는 전면 교체를 묶지 않는다.
코루틴·이벤트·상태 관찰은 생명주기와 취소를 명확하게 관리한다.

## 단계별 작업

1. 요청한 단계와 선행 완료 상태, 현재 브랜치와 사용자 변경을 확인한다.
2. 해당 단계의 범위와 완료 기준을 짧게 정리한다.
3. 명확하게 요청받은 구현 범위 안에서 조사·수정·검증을 진행한다.
4. 의미 있는 실패와 예외를 처리하고 실제 결과를 확인한다.
5. 진행표에 구현·검증·외부 조건·다음 준비 상태를 기록한다.
6. 변경한 사용자 동작, 검증 결과와 남은 조건을 간결하게 보고한다.

“NN단계를 구현하고 검증까지 진행”이라는 요청은 그 문서에 정의된 범위의 작업 지시다.
새롭게 필요한 사용자 결정은 진행 가능한 부분을 정리한 뒤 구체적인 선택과 영향을 묻는다.
계획만 요청받은 경우 결과는 계획이며 앱 기능을 변경하지 않는다.

- 사용자 변경, 기존 작업 공간, 원본 데이터와 기록을 보존한다.
- 기능 작업의 기준 브랜치는 develop이며 main 직접 변경을 피한다.

- 적절한 기존 작업 공간을 확인하고 격리가 필요할 때 새 작업 공간을 사용한다.
- 이관은 중복 실행·중단·재시작을 고려하고 기존 기록의 불확실성을 유지한다.
- 운영 데이터 삭제, 공개 배포, 외부 메시지 전송은 해당 행동에 대한 지시 범위에서 수행한다.
- 비밀값, 이메일, 패키지명, 화면 내용과 사용자 입력을 로그나 문서에 노출하지 않는다.

- 변경 범위에 필요한 시간·상태·동시성·이관·소유권·결제 테스트를 실행한다.
- 실제 제한·예약·해제·권한 복귀·구매·복원은 해당 기기와 플랫폼에서 확인한다.

- 디버그 검증과 출시 빌드·코드 축소 후 검증을 구분한다.
- 추가 검증 도구와 명령은 실제 확인한 것만 이 문서나 연결된 안내에 등록한다.
- 실행하지 못한 검증은 미검증으로 표시하고 이유와 필요한 조건을 남긴다.
- 단계 전체의 완료 기준이 충족될 때만 완료로 표시한다.
- 구현 완료·기기 검증 완료·스토어 승인·공개 배포 완료를 서로 구분한다.

## 6. 마지막 단계에서 확인할 사항

1. develop을 기준으로 계속 사용하는지, 코드 경로가 변경됐는지 확인하고 초안을 수정한다.
2. verify.sh에 실제로 포함된 검증과 플랫폼별 추가 검증을 확인한다.
3. 새 로컬 저장·클라우드 계약·서버 소스의 실제 위치를 연결한다.
4. 코드·화면·상품·기획의 현재 상태와 지침이 일치하는지 확인한다.
5. 이전 agent.md나 다른 경로의 override에 상충하는 승인·작업 규칙이 남아 있는지 확인한다.
6. 새 작업에서 어떤 지침을 읽었는지 확인한다. 문서에 썼다는 사실만으로 자동 적용을 단정하지 않는다.

지침의 길이는 약 100줄 안팎을 출발점으로 삼되 이는 제품 권고다. 필요한 원칙을 생략하기 위해 줄 수를 맞추지 않는다. 장기적으로 유지하는 내용은 루트 지침에, 자주 변하는 단계 상태와 검증 결과는 연결된 문서에 둔다.
