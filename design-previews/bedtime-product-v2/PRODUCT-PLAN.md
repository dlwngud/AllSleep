# AllSleep 취침 행동 중심 제품 개편 기획서

작성일 2026년 10월 12일 · 제안 버전 2.0 · Android 우선 출시

이 문서는 기존 앱의 색감과 캐릭터를 유지하면서 기능, 정보 구조, 사용 흐름, 유료 상품을 다시 설계하는 제품 명세다. 화면 시안은 제안이며 현재 앱의 구현 상태가 아니다. 가격, 성과 수치, 기록, 사용자 이름은 검증 전 가설 또는 시안용 예시다. 실제 수면을 측정하거나 치료 효과를 약속하지 않는다.

## 1. 제품이 해결할 문제

사용자는 자야 한다는 것을 알지만 영상, SNS, 게임을 계속 사용하며 자신이 정한 취침 시간을 넘긴다. “오늘은 일찍 자야지”라는 결심이 밤마다 다시 필요한 구조가 문제다. 여러 기기를 가진 사용자는 한 기기를 내려놓고 다른 기기로 옮겨가기도 한다.

AllSleep의 역할은 사용자가 낮에 정한 선택을 밤에 실행하기 쉽게 만드는 것이다. 목표 시간 전에 마무리를 안내하고, 그 시간이 되면 미리 선택한 앱의 사용을 제한하고, 다음 날 결과에 따라 작은 조정을 돕는다. 사용 시간을 늘리는 대신 밤의 사용을 끝내는 제품으로 설계한다.

**제품 약속:** 정한 시간이 되면 디지털 사용을 마무리하고 잠자리에 들도록 돕는다.

**사용자가 얻는 결과:** 매일 다시 결심하는 부담 감소, 취침 전 앱 사용 제한, 다른 기기로 옮기는 우회 감소, 자신의 계획을 지켰는지 확인.

**기획 경계:** 잠금 확인은 실제 잠듦의 확인이 아니다. 잠금 유지 시간은 실제 수면 시간과 다르다. 침대에 들었는지는 선택적인 본인 확인으로만 수집한다.

## 2. 타깃과 사용 상황

### 2.1 초기 타깃

자신의 취침 지연 원인을 스마트폰 사용으로 인식하고, 일정한 기상 시간이 있으며, 앱 제한을 스스로 선택할 의향이 있는 성인. 연령 가설은 20대부터 40대지만 실제 모집은 연령보다 행동 조건을 우선한다. 첫 출시에서는 자녀 통제, 가족 감시, 수면 장애 치료, 회사 단말 관리까지 확장하지 않는다.

### 2.2 대표 상황

| 상황 | 현재의 마찰 | 필요한 결과 | 제품 대응 |
| --- | --- | --- | --- |
| 침대에서 영상 한 편을 더 봄 | 앱 안에서 종료 계기가 없음 | 정한 시각에 사용을 끝냄 | 마무리 알림과 선택 앱 제한 |
| 폰을 내려놓고 태블릿을 켬 | 기기별 제한이 흩어짐 | 지원 기기를 같은 일정으로 제한 | Plus 기기 연동과 개별 실행 확인 |
| 야근이나 약속으로 일정이 달라짐 | 반복 설정을 바꾸거나 앱을 끔 | 오늘만 예외를 만들고 내일 복귀 | 오늘만 변경과 자동 만료 |
| 잠금 중 필요한 업무가 생김 | 모든 제한 해제 또는 앱 삭제 | 필요한 앱만 잠깐 사용 | 5분 임시 사용과 즉시 긴급 접근 |
| 며칠 실패하고 포기함 | 점수와 연속 기록이 죄책감을 줌 | 무리 없는 목표로 다시 시작 | 원인 한 가지와 작은 조정 제안 |

### 2.3 해야 할 일

“내일 일정 때문에 자야 하는 밤에, 한 번 더 볼까 하는 순간마다 의지력을 쓰지 않고, 미리 정한 계획대로 기기 사용을 끝내고 싶다.”

## 3. 제품 설계 원칙

1. 첫 잠금 성공까지 로그인과 결제를 요구하지 않는다. 로컬 저장이 실제로 동작하는 게스트 사용을 제공한다.
2. 앱 전체를 무조건 봉쇄하기보다 사용자가 선택한 취침 방해 앱을 제한한다. 전화와 필요한 기능은 계속 접근할 수 있다.
3. 주요 버튼은 화면당 하나다. 밤에는 설명과 꾸밈을 줄이고 행동을 짧게 만든다.
4. “시작 요청”, “이 기기에서 실행 확인”, “다른 기기 응답 대기”를 구분한다. 서버에 상태가 저장됐다는 이유만으로 모든 기기가 잠겼다고 표시하지 않는다.
5. 긴급 접근, 권한 복구, 해제, 데이터 조회와 삭제는 결제 여부와 관계없이 제공한다.
6. 기록은 사실과 자기 보고를 나눠 표시한다. 의료적인 수면 효율, 수면 부채, 깊은 수면을 추정하지 않는다.
7. 실패를 사용자 탓으로 돌리지 않는다. 기술적 실패, 사용자가 선택한 종료, 긴급 접근을 서로 다른 결과로 기록한다.
8. 밤에 사용 시간이 늘어나는 장치와 광고를 넣지 않는다. 유료는 반복 사용에서 생기는 추가 가치를 판매한다.

### 4.1 새 개편에서도 추가하지 않을 기능

백색소음·수면 음악 라이브러리, 명상 콘텐츠 구독, AI 대화 코치, 친구 순위와 경쟁, 낮의 공부 타이머, 캐릭터 수집과 출석 보상은 초기 제품에서 제외한다. 밤에 화면을 더 보게 하거나, 핵심 잠금과 루틴의 신뢰성을 확보할 개발 여력을 분산하기 때문이다. 음악은 필요하면 항상 허용 앱으로 접근하게 한다. 건강 플랫폼 연동은 잠금 기록만으로 수면을 단정하지 않는 기본 경험을 완성한 뒤 별도 문제와 수요를 검증한다.

## 6. 핵심 사용 순환

낮에 일정과 제한 앱을 선택한다 → 취침 15분 전 사용을 마무리한다 → 정한 시각에 제한이 시작된다 → 필요한 앱만 예외로 사용한다 → 아침에 결과를 확인한다 → 반복해서 늦어진다면 일정을 작게 조정한다.

### 6.1 최초 사용

앱 시작 → 가치 소개 → 방해 원인 선택 또는 건너뛰기 → 취침·해제 시각 → 제한 앱 → 권한 준비 → 10초 테스트 → 오늘 준비 완료 → 홈.

원인 선택은 선택 항목이다. 로그인과 유료 소개는 이 흐름에 끼워 넣지 않는다. 권한을 거절하면 계획과 기록 화면은 이용할 수 있고 제한은 실행되지 않는다는 상태를 보여준다. “나중에 준비하기”로 홈에 진입할 수 있다.

### 6.2 매일 밤

마무리 알림 → 즉시 시작 또는 한 번 미루기 → 설정한 시각 → 이 기기 실행 확인 → 제한 중 → 해제 시각 또는 명시적 종료. 자동 실행이 플랫폼 제약으로 실패하면 “아직 시작되지 않았어요” 알림과 앱 진입 경로를 제공한다.

### 6.3 수익 전환

본인 요청으로 기기 추가 또는 복수 루틴 선택 → 필요한 가치 설명 → 게스트면 로그인 → 해당 기기의 권한·기능 지원 확인 → 상품 비교 → 선택한 요금제의 결제 조건 확인 → 스토어 결제 → 구매 검증 → 사용 설정.

주간 개선에서 제안하는 유료 안내는 충분한 기록이 있을 때 낮에만 노출한다. 기록 화면을 가리지 않으며 사용자가 닫을 수 있다. 자동 유료 안내는 7일에 1회 이하, 같은 안내를 두 번 거절하면 30일 중단하는 가설을 검증한다. 직접 선택한 유료 기능의 설명은 이 빈도 제한과 별개다.

## 7. 정보 구조와 화면 목록

하단 탭은 **오늘 / 루틴 / 기록 / 마이** 네 개다. 오늘은 지금 할 일, 루틴은 앞으로의 계획, 기록은 지난 결과, 마이는 계정·기기·구독·설정이다. 제한 실행 중에는 하단 탭을 숨기고 필요한 접근·종료만 제공한다.

화면 ID와 목적, 구성, 행동, 예외, 검수 기준은 `SCREEN-SPEC.md`에 제공한다. `index.html`의 화면 탐색과 전체 시안에 같은 ID를 사용한다. 전체 화면 수는 화면 데이터 기준으로 자동 집계한다.

## 8. 주요 기능의 상세 규칙

### 8.1 취침 약속과 기준 시각

사용자가 선택한 취침 시각을 사용 제한 목표 시각으로 저장한다. 해제 시각은 제한 종료 시각이며 기상 알람과 별도 설정이다. 예시 기본값 23:30과 07:00은 시안 데이터로만 쓰고, 실제 사용에서는 명시적 사용자 확인을 받는다.

기본 루틴 1세트 안에 평일과 주말 설정을 무료 제공한다. 요일은 취침 시작 날짜의 요일을 기준으로 한다. 월요일 23:30부터 화요일 07:00까지는 월요일 회차다. 오늘만 변경은 회차 ID에 붙으며 한 번 사용 또는 취소 후 만료된다.

취침 전 30분보다 이전에 확정한 시각을 분석용 약속 시각으로 스냅샷한다. 이후 변경은 사용자에게 허용하지만 원래 약속과 변경 시각을 모두 기록한다. 사후 수정으로 정시 달성률을 높이지 않는다. 앱 표시용 “오늘 계획”과 분석용 “처음 약속”을 구분한다. 첫날처럼 30분 전에 계획이 없었다면 분석 분모에 넣지 않고 “첫 사용”으로 표시한다.

같은 시작·해제 시각은 24시간 제한으로 오해하지 않게 저장을 막는다. 시작에서 다음 해제까지의 최대 제한 길이는 초기 16시간 가설로 설정하고 확장 여부를 사용자 검증한다. 이미 지난 시각은 오늘 적용인지 다음 회차인지 날짜를 보여주고 확인한다. 일정이 겹치면 우선 적용할 루틴을 직접 선택하게 한다.

시간대 변경을 감지하면 현재 회차는 저장된 절대 해제 시각을 유지하고, 다음 회차는 현지 시각에 따라 재계산한다. 변경 사실을 안내하고 수정할 수 있게 한다. 일광절약 시간 중 없는 시각이나 중복 시각은 실제 다음 날짜·시각을 표시하고 확인한다.

### 8.2 제한 대상과 허용 앱

온보딩에서 설치된 앱 중 사용자가 실제로 방해받는 앱을 선택한다. 기본 선택은 없고 추천 범주는 영상·SNS·게임이다. 브라우저도 사용자가 선택할 수 있으나 웹사이트 단위 차단은 검증 전 출시 혜택에 넣지 않는다.

항상 허용 목록은 전화, 긴급 기능, 인증 수단, 지도 등 사용자가 필요한 앱으로 구성한다. 전화와 OS 긴급 기능은 제품이 가로막지 않는다. Android에는 시스템 앱을 무조건 모두 허용하는 현재 방식 대신 실제 필요한 예외와 플랫폼 안전 예외를 구분한다. iOS는 OS 선택기와 지원된 Shield 범위로 구현한다.

제한 앱과 항상 허용 앱이 충돌하면 허용이 우선이다. 저장 전에 충돌 앱과 결과를 알려준다. 잠금 화면의 버튼이 실제 허용 앱까지 도달하는지를 실기기에서 확인한다. 앱 삭제·새 설치에 따른 대상 목록 변화를 반영한다.

### 8.3 마무리와 미루기

15분 전 알림은 “23:30에 사용 제한이 시작돼요. 지금 보고 있는 걸 마무리해요.”로 표현한다. 알림 자체에서 지금 시작 또는 10분 뒤 시작을 선택할 수 있다. 기본 미루기 1회 후에는 추가 미루기를 같은 위치에서 반복 제안하지 않고 오늘만 변경으로 이동한다. 사용자는 여전히 직접 계획을 수정할 수 있다.

차분한 제한은 5분 임시 사용 확인을 허용한다. 신중한 제한은 일반 조기 종료에 이유 선택과 다시 확인을 둔다. 시간 강제 대기·퀴즈·광고·결제를 종료 조건으로 쓰지 않는다. 긴급 접근은 어떤 방식에서도 즉시 실행한다.

### 8.4 시작과 종료의 상태 모델

`준비 필요 → 예약됨 → 시작 요청 → 이 기기 실행 확인 → 제한 중 → 종료 요청 → 해제 확인 → 기록 완료`가 기본 흐름이다. 요청 후 3초에는 “확인 중”, 10초에는 지연 안내, 20초에는 상태 재확인과 재시도를 제공한다. 이 시간들은 UX 가설이며 기기별 검증 후 조정한다. 응답이 오지 않은 경우 실패가 확정됐다고 단정하지 않고 “확인되지 않음”으로 표현한다.

시작과 종료는 회차 ID와 명령 버전으로 중복 실행을 막는다. 늦게 도착한 시작 명령이 최신 종료 명령을 덮지 않는다. 제한이 확인되기 전에는 성공 이모지나 완료 문구를 보여주지 않는다. 재시작 후에는 로컬 상태와 OS 실행을 재확인하고 남은 해제 시각을 복구한다. 클라우드 연결이 끊겨도 이미 저장된 로컬 일정과 해제는 계속 동작하도록 설계한다.

### 8.5 임시 사용과 긴급 접근

일반 임시 사용은 지정 앱 한 개에 5분을 기본 제공하고 남은 시간과 복귀 상태를 표시한다. 종료 후 적용 확인에 실패하면 전체 제한이 유지됐다고 표시하지 않는다. 5분은 실제 수면이나 의지력에 대한 근거가 아니라 검증할 제품 기본값이다.

긴급 접근은 전화, OS 긴급 기능, 즉시 해제를 제공한다. 이유 입력과 카운트다운은 요구하지 않는다. 다른 기기에 해제 요청을 보낼 수 있지만 원격 응답을 기다리느라 이 기기의 해제를 지연하지 않는다. 사후 기록에서 긴급 종료는 별도 결과이며 부정적인 문구나 연속 기록 손실 경고를 사용하지 않는다.

### 8.6 여러 기기

연동은 계정으로 연결된 지원 기기에서만 동작한다. Android부터 제공하고 iOS는 별도 개발·승인·검증 후 포함한다. 컴퓨터, TV, 게임기까지 제한한다고 약속하지 않는다. 등록만 되어 있거나 오래된 상태를 “준비 완료”로 표시하지 않는다.

기기별로 등록 상태, 지원 여부, 권한, 최근 응답, 일정 버전, 현재 실행, 해제 시각을 표시한다. 2분 이내 상태 갱신은 “최근 확인”, 2분 초과는 마지막 확인 시각 표시라는 초기 가설을 두되 배터리 비용에 맞춰 검증한다. 마지막 응답이 최신 명령 이전이면 그 명령의 완료를 증명하지 못한다.

연결 코드는 6자리, 5분 만료 가설, 한 번 사용 후 폐기, 시도 횟수 제한을 적용한다. 코드만으로 즉시 다른 계정의 기기를 붙이지 않는다. 양쪽 계정과 기기 이름을 확인하고 승인한다. 해제한 기기는 해당 계정의 새 명령과 기록에 접근하지 못한다. 오프라인 기기는 저장된 로컬 제한이 가능할 수 있으나 원격 완료는 확인되지 않는다고 표시한다.

구독 만료 시 이번에 실행 중인 회차와 모든 기기의 예정 해제는 보존한다. 다음 회차부터 주 기기 한 대의 무료 루틴만 활성화한다. 사용자가 주 기기를 선택할 수 있게 하고 기타 기기의 자동 실행이 꺼진 사실을 각 기기에 표시한다. 갑작스러운 잠금 해제나 해제 불능이 발생하지 않게 한다.

## 9. 기록과 개선

### 9.1 기록의 정의

| 항목 | 관찰 근거 | 표시 |
| --- | --- | --- |
| 약속 시각 | 사용자 일정 스냅샷 | 처음 약속 23:30 |
| 실제 제한 시작 | 기기의 실행 확인 | 이 기기 제한 시작 23:38 |

관찰 공백은 “확인되지 않음” 구간이다. 잠금 요청 시각부터 전체 종료까지를 무조건 유지 시간으로 계산하지 않는다. 하루 상세에 실제 확인된 구간과 공백을 표시한다. 다중 기기의 유지 시간은 합산하여 부풀리지 않고 기기별 기록과 전체 준비 여부를 분리한다.

### 9.2 무료 기록

모든 본인 원본 기록, 날짜별 상세, 최근 7일 정시 시작 일수, 평균 시작 지연, 임시 사용 횟수를 제공한다. 원본 기록을 오래됐다는 이유로 가리지 않는다. 기록 없음은 0점으로 표현하지 않는다. 성공·실패 색상만으로 결과를 전달하지 않는다.

### 9.3 Plus 개선

최근 28일 비교, 요일별 패턴, 복수 루틴별 결과, 7일 조정 계획을 제공한다. 첫 비교는 분석 가능 기록 7개 이상, 기간 비교는 각각 최소 3개의 유효 회차가 있는 경우라는 가설을 둔다. 데이터가 부족하면 부족한 기록 수를 안내하며 유료 안내로 빈 그래프를 채우지 않는다.

예를 들어 반복해서 20분 늦어진 경우 “취침 준비를 10분 앞당겨 볼까요?”라는 한 가지 제안을 한다. 사용자가 적용 전 기존 일정·제안 일정·기간을 비교하고 동의해야 한다. 적용 후 결과를 함께 보여준다. 규칙 기반 제안을 AI 코칭이라고 부르지 않는다.

결제의 이유는 광고 제거, 강한 통제, 데이터 인질이 아니라 여러 환경에서도 반복적으로 취침 계획을 유지하는 편의다. 백업을 무료로 두어 기기 교체가 기록 손실로 이어지지 않게 한다.

### 10.2 가격 가설

한국 초기 가설은 월 4,900원, 연 39,000원이다. 연 요금은 1년에 한 번 39,000원 결제이며 월 환산 3,250원은 보조 정보다. 월 요금 12개월 대비 약 34% 낮다. 이는 경쟁사 가격을 복제한 것이 아니라 인터뷰와 결제 실험으로 검증할 제안이다.

월 요금제를 기본 선택해 체험과 장기 결제를 혼동하지 않게 한다. 연간 요금제의 7일 체험은 스토어에서 실제 자격이 확인된 사용자에게만 제공한다. 체험이 없는 월간 선택의 CTA는 “월 4,900원으로 구독”이며 연간 체험 CTA는 “7일 체험 후 연 39,000원”이다. 체험 자격이 없으면 “연 39,000원으로 구독”으로 바뀐다. 단순히 모든 사용자에게 무료 체험을 약속하지 않는다.

연간 체험 선택 시 기간, 다음 결제일, 연간 총액, 자동 갱신, 해지 경로를 CTA 가까이에 함께 표시한다. 가격은 스토어 조회값을 사용한다. 가격 로딩 실패 때 예시 가격으로 결제를 진행하지 않는다. 결제 취소는 오류가 아니다. 구매 확인이 지연되면 다시 구매를 유도하지 않고 검증·복원을 제공한다. 화면 시안의 10월 19일 결제는 10월 12일 시작 예시에 해당하며 실제 앱은 스토어 조건과 시간대를 기준으로 계산한다.

### 10.3 전환과 해지 화면

가치 소개 → 요금 선택 → OS 결제 시트 → 서버와 스토어 검증 → 사용 설정 완료. OS 결제 시트 시안은 맥락 설명을 위한 시스템 예시이며 자체 결제창을 흉내 내어 청구하지 않는다. 관리 화면은 상품, 갱신일, 스토어, 복원, 해지 이동을 보여준다. 해지를 선택하면 스토어 관리로 직접 연결한다. 설문은 선택이며 앞을 가로막지 않는다.

해지 예정 상태는 이용 가능 마지막 날짜를 표시한다. 만료 후에는 무료로 계속 사용할 기기를 선택한다. 데이터와 기존 무료 루틴은 보존한다. 탈퇴는 스토어 구독 해지와 별개임을 설명하되 구독 관리 버튼과 계정 삭제 버튼을 함께 제공하고 탈퇴를 결제 해지 여부로 차단하지 않는다.

### 10.4 사업성 시나리오

다음은 계산 예시이며 실제 매출 예측이나 수수료 확정값이 아니다. 월 활성 사용자 중 유료 전환이라는 동일한 분모를 사용한다. 모든 유료 사용자가 월간이라고 가정한 단순 계산이다.

| 월 활성 | 유료 전환 가정 | 유료 인원 | 월 청구 총액 | 공제 15% 가정 후 | 공제 30% 가정 후 |
| --- | --- | --- | --- | --- | --- |
| 10,000명 | 2% | 200명 | 980,000원 | 833,000원 | 686,000원 |
| 10,000명 | 5% | 500명 | 2,450,000원 | 2,082,500원 | 1,715,000원 |
| 50,000명 | 5% | 2,500명 | 12,250,000원 | 10,412,500원 | 8,575,000원 |

연간 가입자의 기간 배분 매출은 월 3,250원으로 계산하며 실제 현금 수입은 연 결제 시점에 집중된다. 유료 500명 중 월간 60%, 연간 40%라면 기간 배분 총액은 `300 × 4,900 + 200 × 3,250 = 2,120,000원/월`이다. 세금, 환불, 결제 실패, 백엔드, 고객지원, 마케팅, 개발 비용은 별도로 차감한다. 15%와 30%는 비교용 가정이고 실제 스토어 프로그램·국가·계약에 따라 확인한다.

초기에는 평균 구매 전환보다 첫 주 가치 경험과 유료 유지 이유를 먼저 검증한다. 3개월 유료 이탈과 실제 한계이익을 보기 전에는 LTV를 확정하거나 공격적으로 유료 유입을 늘리지 않는다.

## 11. 성공 지표와 계측

### 11.1 핵심 지표

주요 행동 지표는 **유효한 약속 회차 중 목표 시각 10분 이내에 선택 앱 제한이 확인된 회차 비율**이다. 이것은 수면 개선율이 아니다. 10분 허용은 분석 가설이다. 중간 임시 사용과 조기 종료는 별도 표시하며 “처음 정시에 시작”과 “끝까지 유지”를 혼동하지 않는다.

유효 회차는 사용자가 취침 30분 전에 확정한 계획이며 기술적 관찰이 가능한 회차다. 기술 실패·권한 철회·관찰 공백은 행동 성공 분모에서 제외해 따로 보고하되 전체 계획 대비 실행 성공률에는 포함한다. 긴급 종료도 독립 집계한다. 분모에서 제외된 비율을 항상 함께 공개하여 성공률을 부풀리지 않는다.

| 지표 | 분모 | 목적 | 초기 검증 기준 가설 |
| --- | --- | --- | --- |
| 첫 설정 완료 | 첫 가치 소개 진입 | 설정 마찰 확인 | 60% 이상 |
| 첫 실행 확인 | 설정 완료 사용자 | 핵심 경험 제공 | 70% 이상 |
| 기술 실행 성공 | 모든 시작 요청 | 제품 신뢰 | 99% 목표, 플랫폼별 별도 |
| D7 행동 유지 | 첫 실행 확인 사용자 | 반복 가치 | 35% 이상이 7일 차에 유효 회차 보유 |
| 정시 시작 변화 | 동일 사용자의 1주·3주 유효 회차 | 행동 변화 탐색 | 개인 내 변화 관찰, 인과효과로 단정 금지 |
| 유료 전환 | 해당 유료 가치 설명 방문 사용자 | 상품 적합도 | 5% 가설 |
| 체험 유료 전환 | 체험 시작 사용자 | 체험 가치 | 25% 가설 |
| 유료 3개월 유지 | 유료 시작 코호트 | 지속 수익 | 파일럿에서 기준 설정 |

이 수치는 업계 평균이나 보장치가 아니다. 파일럿에서 기준을 바꾸며 기술 실패와 실제 이탈을 분리한다. 사용자의 앱 체류 시간은 늘릴 목표로 삼지 않는다.

### 11.2 최소 이벤트

`onboarding_step_view`, `onboarding_complete`, `routine_saved`, `permission_result`, `lock_test_result`, `session_requested`, `device_execution_confirmed`, `session_unconfirmed`, `winddown_action`, `snooze_used`, `temporary_access`, `session_ended`, `morning_checkin`, `paywall_view`, `plan_selected`, `purchase_result`, `restore_result`, `entitlement_changed`, `routine_adjustment_applied`.

제품 분석 이벤트에는 패키지명, 화면 내용, 메시지, 이메일, 로그인 비밀번호, 기기 별명, 긴급 이유를 보내지 않는다. 회차 ID는 제품 내부 중복 방지 용도로 사용하며 분석에는 회전 가능한 익명 ID와 거친 결과값만 사용한다. 개인 정보 고지와 실제 전송 범위가 일치해야 한다.

### 11.3 실험

첫 사용은 “원인 질문 포함”과 “질문 건너뛰기”의 설정 완료·첫 실행·다음 주 유지로 비교한다. 결제는 첫 성공 후 직접 기기 추가, 7일 기록 후 낮의 비교 제안 두 맥락을 비교한다. 가격 테스트는 월 3,900·4,900·5,900원 중 별도 코호트로 시행하며 같은 사용자에게 이유 없이 다른 가격을 제시하지 않는다. 주간 제안은 변경 전·후 자기 보고와 행동 기록을 함께 확인한다.

## 13. 플랫폼과 출시 범위

### 13.1 Android 먼저 완성

접근성 서비스를 통해 선택 앱 실행을 감지하는 현재 방향은 사용자 선택에 따른 좁은 목적과 명확한 고지로 설계한다. 접근성 도구인 것처럼 표시하지 않는다. 권한 고지에는 어떤 정보를 접근하며 어떻게 쓰는지 별도 화면에서 설명하고 명시적 동의를 받는다. 이 사용에 필요한 Play 선언과 심사는 출시 조건이다. [Google Play AccessibilityService 안내](https://support.google.com/googleplay/android-developer/answer/10964491)

백그라운드 실행과 자동 시작은 OS 버전·제조사별 검증이 필요하다. Android의 전경 서비스 시작 제한을 고려하고, 오버레이 권한만 있으면 예약 자동 시작이 항상 가능한 것으로 취급하지 않는다. 실패 시 준비 상태와 실행 여부를 실제 확인해 표시한다. [Android 전경 서비스 변경사항](https://developer.android.com/develop/background-work/services/fgs/changes)

### 13.2 iOS는 동등한 기능을 자동으로 약속하지 않음

개인 사용자의 Screen Time 권한, FamilyControls, DeviceActivity, ManagedSettings 경로를 별도 검증한다. 개인 사용자는 권한을 철회할 수 있으므로 해제 불가능한 통제를 약속하지 않는다. 앱 및 필요한 확장의 배포 권한 승인과 실기기 테스트를 완료하기 전에는 iOS 기기를 유료 동시 제한 혜택에 포함하지 않는다. [Apple 개인 승인 설명](https://developer.apple.com/videos/play/wwdc2022/110336/), [배포 권한 요청](https://developer.apple.com/documentation/FamilyControls/requesting-the-family-controls-entitlement)

### 13.3 판매 조건의 정확성

요금, 결제 주기, 자동 갱신, 체험 종료 후 가격, 해지 경로를 결제 전에 표시한다. 지속적인 가치를 제공하며 무료 사용 경로를 명확히 둔다. 가격과 자격은 실제 스토어에서 확인한다. [Google Play 구독 정책](https://support.google.com/googleplay/android-developer/answer/9900533)

## 14. 데이터와 계정

기본 설정과 기록은 로컬에 저장한다. 로그인하면 선택적으로 백업한다. 접근성 이벤트로 얻는 앱 실행 판별 정보는 제한 목적에 필요한 최소 범위에서 기기에 처리하고 화면 내용·입력 문장은 수집하지 않는 방향으로 구현한다. 현재 구현과 일치하는지 감사한 뒤 고지한다.

게스트 데이터는 로컬 소유자 ID를 가진다. 로그인 후 회차 ID로 중복 제거하고, 병합 전 원본을 보존한다. 클라우드 기록과 충돌하면 일정은 사용자 선택, 기록은 고유 회차 기준 합친다. 다른 계정으로 바꾸면 이전 계정 데이터는 분리하며 임의로 합치지 않는다.

지원에 첨부하는 진단 정보는 앱 버전, OS, 권한·서비스 상태, 에러 코드 정도다. 첨부 여부를 사용자가 선택하고 앱 사용 상세는 자동 전송하지 않는다. 데이터 내보내기, 원본 삭제, 계정 삭제와 진행 상태를 제공한다. 오프라인 삭제 요청은 접수·완료를 구분한다. 보존 기간과 삭제 SLA는 서비스 운영 정책으로 확정할 항목이며 현재 시안에서 임의의 기간을 약속하지 않는다.

## 16. 예외 처리와 화면 상태

모든 목록은 로딩·정상·비어 있음·부분 데이터·오류·오프라인을 정의한다. 기존 데이터가 있으면 오류 때문에 삭제하거나 빈 화면으로 덮지 않는다. 재시도는 입력과 선택을 보존한다. 인증·가격·권한 실패는 해당 기능만 제한하며 기록과 무료 로컬 기능을 막지 않는다.

중복 탭은 한 번의 요청으로 처리한다. 화면 이동이나 취소 후 늦은 응답이 화면을 임의로 바꾸지 않는다. 결제에서 돌아오면 구매 확인 후 성공 표시, 권한 설정에서 돌아오면 실제 권한 조회 후 준비 상태 변경을 한다. 설정 복귀만으로 의도하지 않은 제한을 자동 시작하지 않는다.

## 17. 출시 단계

### 단계 A 핵심 경험

Android 게스트 사용, 기본 루틴, 제한 앱, 권한·테스트, 자동 실행 확인, 예외 접근, 아침 기록을 완성한다. 광고와 수면을 과장하는 통계를 제거한다. 첫 회차가 정상적으로 시작·끝나는지 실기기에서 검증한다. 기술 실패가 행동 실패로 기록되지 않아야 한다.

### 단계 B 수익 기능

계정 병합·백업, Android 여러 기기, 복수 루틴, 주간 비교, 정확한 구매·복원·만료를 완성한다. 최소 두 대 실기기와 네트워크 단절에서 실행·종료를 검증한다. 상품에 적힌 모든 혜택이 동작할 때 판매한다.

### 단계 C 확장

iOS 개인 권한·Shield·일정 확장 검증과 배포 승인, 위젯, 데이터에 기반한 조정 계획 정교화를 진행한다. iOS 제한 기능이 준비되지 않으면 Android 기기만 연결 가능한 범위를 명시한다.

## 19. 먼저 검증할 불확실성

다중 기기를 실제로 오가는 사용자의 비중, 사용자가 허용하는 제한 방식, 선택 앱 제한만으로 취침 사용을 줄일 수 있는지, 주간 개선에 돈을 낼 이유, Android 자동 시작의 제조사별 안정성, iOS 배포와 연동 범위는 아직 검증되지 않았다. 시안은 이 가설을 숨기지 않는 설계다.

초기 인터뷰 8~12명, Android 2주 사용성 파일럿 20~30명, 첫 주 행동 기록, 실제 결제 의향을 차례로 확인한다. 표본 수는 운영 계획 가설이다. 인터뷰에서 문제의 강도를 확인하고, 파일럿에서는 실제 행동과 기술 실패를 분리하며, 가격은 가치 경험 후 질문한다.

## 20. 제공 산출물

- `index.html`: 화면 탐색, 주요 사용 흐름, 전체 화면 갤러리, 디자인 기준. 모든 행동은 시뮬레이션이며 실제 잠금·인증·결제가 아니다.
- `SCREEN-SPEC.md`: 각 화면의 목적, 구성, CTA, 이동, 예외와 검수 기준.
- `PRODUCT-PLAN.md`: 본 제품·기능·수익·측정·운영 기획서.
- `output/pdf/allsleep-design-book.pdf`: 화면 시안과 화면별 구현 메모를 묶은 디자인북.
- `output/pdf/allsleep-product-plan.pdf`: 공유용 기획서.
- `overview.png`: 대표 흐름을 비교할 수 있는 시안 보드.

기존 앱 소스는 이 제안 작성 과정에서 변경하지 않는다. 재설계 범위를 별도 산출물로 남겨 제품 방향을 검토하고 이후 구현의 기준으로 사용할 수 있게 한다.
